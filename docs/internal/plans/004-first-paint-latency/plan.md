# 004-first-paint-latency 実装計画

## 背景と目的

M5 ドッグフーディングの「一覧なし→初回表示までの間(コマンド名で顕著)」
(`../001-prototype/notes-dogfooding.md` 2026-07-28。使用をためらうレベル)を解消する。

2026-07-29 の計測(`tests/zsh/driver-latency.zsh`)で内訳は確定済み:

- コマンド名 first-paint ~192ms = デバウンス 52 + spawn 7〜22 + **compsys 92〜107** + match ほか 15〜30。
- compsys の 92ms は typo 許容のための**広げ収集**(空語で全コマンド名 ~4000 件を生成)が原因。
  as-typed 模擬では同じ compsys が 16ms。
- zsh-autocomplete は同型アーキテクチャ(デバウンス → fork → 内部 zpty で compsys)だが
  as-typed 収集のためこのプレミアムを払わない。

本計画は「**空語(コマンド位置)収集のキャッシュ**」でこのプレミアムを排除し、
あわせてキャッシュ後の実測に基づいて `delay-ms` の既定値を再調整する。
目標: コマンド名の first-paint をヒット時 ~70ms 以下(デバウンス + キャッシュ検証 + match)へ。

## 決定事項

- **キャッシュ対象は「広げ結果が空文字列」の収集のみ**(= 行頭のコマンド位置)。
  - 計測した高コストケースはすべてこれに該当する。
  - `sudo ` や `&&` 後などのコマンド位置は広げ結果が別文字列であり対象外
    (任意文脈への一般化は無効化問題が別次元になるため将来拡張とする)。
  - 収集 fork は「LBUFFER=広げ文字列、RBUFFER=空」で駆動されるため、
    空語収集の結果は広げ文字列以外のバッファ状態に依存しない(キーの成立根拠)。
- **キャッシュはプロンプト(コマンド行)を跨いで保持する**。
  - 苦情の本体は「新しい行で最初に打ったときの初回表示」であり、行内 2 回目以降の
    更新は 002 の置き換え更新モデルで既に視覚的に平滑。行内キャッシュでは的を外す。
- **無効化は使用時フィンガープリント + TTL ベルト**。
  - フィンガープリント = `$PATH` 文字列 + PATH 各ディレクトリの mtime(zstat)
    + `$#functions` + `$#aliases` + `$#builtins`。計算コスト ~1ms(ヒット利得 75ms に対し無視可能)。
  - **ディレクトリ mtime がバイナリの追加・削除を拾う**(`brew install` 直後も次の打鍵で反映)。
    `rehash` は集合が変わる場合 mtime 変化で拾え、変わらない場合は無視してよい。
  - `$#commands` は使わない(zsh のコマンドハッシュは遅延充填で、実行のたびに
    集合と無関係にサイズが育つため)。
  - TTL(既定 300 秒、固定値・設定項目にしない)は「同数の入れ替わり」
    (関数を 1 個消して 1 個定義した等、カウントが動かない変化)の保険。
  - 検証はキャッシュ使用時に行う(precmd フック不要・自己完結)。
  - **PWD の条件付き参入**: `autocd` が有効、または `$PATH` に相対要素
    (`.`・空要素・非絶対パス)がある場合のみ `$PWD` をフィンガープリントに含める
    (これらの場合のみ空語候補が PWD に依存し得るため)。通常環境では含めない。
  - **既知の癖(仕様として明記)**: compsys が補完関数(`_git` 等)を遅延ロードすると
    `$#functions` が増えて 1 回余計にミスする。これは正しい無効化
    (ロードされた関数自体がコマンド位置の候補になる)であり、一度きりで収束する。
- **キャッシュ内容は解析済みデータ**: krecs / words / match / disp の各配列と
  `zrush match` 用 stdin ペイロード、およびフィンガープリント。
  - ヒット時にレコード再解析(~5ms)を省く。メモリはシェルあたり ~1MB 強(許容。
    絞る必要が出たら生レコード保持+再解析に落とす)。
  - キャッシュ本体は作業配列(`_zrush_recs` 等。clear_display でクリアされる)とは
    **別の変数**に持つ。
- **フロー変更**: `_zrush_finalize` を「レコード解析部」と「match+render+tab-pending 部」に
  分割し、後半部をヒット経路と共用する。
  `_zrush_start_request` の広げ計算直後に分岐: 空語 && フィンガープリント一致 →
  fork せずキャッシュを積んで後半部を直接呼ぶ。ミス時は従来どおり収集し、
  finalize 成功時にキャッシュを保存する。
  - ヒット経路でも維持する不変条件:
    (1) 進行中の収集はキャンセルする(現行 start_request 冒頭の cancel を通る)、
    (2) タイマー発火の `zle -F -w` 文脈なので表示反映に `zle -R` が必要、
    (3) `_zrush_tab_pending` の適用(後半部共用で自動的に満たす)、
    (4) 世代・stale 破棄の仕組みに触れない。
- **`delay-ms` の既定値は 30 とする**(② の履行。キャッシュ実装後の再計測で決定)。
  - 30ms でのヒット時 first-paint は中央値 65ms(driver-latency 実測)で目標 ~70ms を満たす。
    ファイル・git ケースも 20〜30ms 短縮し、劣化は観測されない。
  - `delay-ms = 0` は連打時にキー処理パスへ収集開始コストが乗り逆効果面がある
    (2026-07-29 計測)ため既定にしない(0〜10000 の設定範囲は不変)。
- config・プロトコルは変更しない(TTL 含め新しい設定項目は作らない。
  `delay-ms` の既定値変更が入る場合のみ config-schema.md の既定値を更新)。

## スコープ外

- fifo の外部コマンド(mkfifo/rm ~8ms)排除。mkfifo に代わる zsh builtin が無く、
  fifo の使い回しは「キャンセルした前リクエストの残骸バイトが次のリクエストへ混入する」
  リスク(EOF フレーミングの前提崩れ)を伴う。将来 match 常駐化を行う際に一緒に解消する。
- 空語以外の文脈(`sudo ` 後など)へのキャッシュ拡張。
- `zrush match` の常駐化(候補集合の resident 化)。キャッシュ後も残る match 往復
  17〜21ms が問題になったときの次の一手として温存。

## 実装手順

1. **C1: finalize 分割リファクタ**(挙動不変)。
   レコード解析部と match+render+tab-pending 部を関数分離し、既存テスト(driver 51 /
   coexist 29 / cargo 71)が全て通ることを確認する。
2. **C2: キャッシュ本体**。
   フィンガープリント関数、ヒット分岐、finalize 成功時の保存、TTL。
   ZRUSH_LOG に hit / miss(理由: fingerprint / ttl / empty)を記録する。
3. **C3: 検証**。
   - driver.zsh: 機能テスト —「2 回目のコマンド位置クエリでヒットする」
     「`alias 追加` / `PATH 追加` / `PATH 上のディレクトリへの実行ファイル追加` の後は
     ミスして新候補が一覧に反映される」を決定的 fixture で確認。
   - driver-latency.zsh: ヒット時 first-paint の計測ケースを追加。
   - coexist / cargo の全既存テスト維持。
4. **C4: `delay-ms` 既定値の再調整**。
   キャッシュ込みで再計測し、既定値を決定(変更する場合は config-schema.md・
   Rust 既定値・テストを同時更新)。

## 受け入れ条件

1. コマンド位置クエリの 2 回目以降(キャッシュヒット)の first-paint が
   **100ms 以下**(driver-latency 実測。目標 ~70ms)。
2. ミス時の挙動・レイテンシが現状から劣化しない(+フィンガープリント ~1ms のみ)。
3. 無効化の正しさ: alias / 関数 / PATH / PATH 上のバイナリの追加・削除が
   次の一覧に反映される(ヘッドレステストで決定的に確認)。
4. Tab 未着時挙動・選択・確定・キャンセル・世代破棄など既存の不変条件が
   ヒット経路でも保たれる(既存 driver 全テスト green)。
5. 実環境ドッグフーディングで「コマンド名の初回表示の間」の体感が解消する
   (notes の該当エントリの判定)。
