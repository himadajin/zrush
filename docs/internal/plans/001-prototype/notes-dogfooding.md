## 気になった挙動

### 2026-07-27 / mac — 選択マーカー(`> `)で一覧全体がずれ、ちらつく [解決]

- 状況: 選択に入ると一覧全体が `> ` の幅だけずれる。選択中も操作のたびにずれ・ちらつきが目につく。
- 期待と実際: 期待は zsh-autocomplete 同等の背景色ハイライト(レイアウトが動かず、選択位置は色で分かる)。実際はマーカー方式でレイアウトが動き、「表示が不安定」という印象が道具への信頼感を下げる。ずれを解消しても(常時字下げ等)マーカー方式では視認性が不足で、期待水準に達しない。
- 備考: `zle -M` 内で ANSI が使えない制約による設計どおりの挙動(plan.md)。使用をためらうレベル。
- 対処: 002-display-layer D1(`feat(zle): replace listing render with POSTDISPLAY + region_highlight`)で
  選択表示を standout ハイライトに置換(レイアウト不動)。2026-07-28 解消を体感確認。

### 2026-07-27 / mac — ctrl+p / ctrl+n で選択移動できない [解決]

- 状況: 選択中に ctrl+p / ctrl+n を押しても候補移動にならない(既定は ↑↓ のみ)。
- 期待と実際: 手癖では上下移動は ctrl+p/n であり、既定で ↑↓ と同様に選択移動に効いてほしい。config の `[keybind]` で変えられるだけでは不足(既定値の問題)。使用をためらうレベル。
- 対処: `[keybind]` を 1 アクション複数キー(文字列 / 配列)に拡張し、既定を
  `["down","ctrl-n"]` / `["up","ctrl-p"]`(select-left/right も `ctrl-b`/`ctrl-f` を追加)へ変更
  (`feat(keybind): multi-key actions with emacs-style defaults`)。2026-07-28 解消を体感確認。

### 2026-07-27 / mac — 候補が縦一列で走査しづらい [解決]

- 状況: 候補が 1 行 1 候補の縦一列で表示される。
- 期待と実際: 一覧を選択メニューとして使うとき、目的の候補を目で探す走査がしづらく、プロンプト下の縦占有も大きい。期待は zsh-autocomplete のような複数列グリッド(一覧性が高く、縦に短い)。使用をためらうレベル。
- 対処: 002-display-layer D2(`feat(display): column-major grid listing and select-left/right`)で
  列優先グリッド+←→の列移動を実装。2026-07-28 解消を体感確認。

### 2026-07-27 / mac — 種別見出し・グループ化がない [解決]

- 状況: 候補の種別(ディレクトリ / ファイル / オプション等)の見出し・グループ化がなく、種別混在で並ぶ。
- 期待と実際: 見ただけで種別が判別できず、同種がまとまらないので目的の候補を探しにくい。期待は zsh-autocomplete の `directory` / `file` のような見出し付きグループ表示。使用をためらうレベル。

### 2026-07-27 / mac — 打鍵ごとの遅延感と、一覧が一瞬消えるチラつき(速度要件未達) [解決]

- 状況: 入力中、打鍵のたびに一瞬の遅延感がある。候補一覧は打鍵のたびに一瞬消えてから描き直され、その空白の瞬間がチラつきとして見える。発生場面の切り分け(候補の多寡・環境差)は未実施。
- 期待と実際: 期待は速度要件どおり「zsh-autocomplete と同等以上」(plan.md)。実際は zsh-autocomplete より遅く感じ、かなり使いにくい。速度要件未達。使用をためらうレベル。
- 未切り分け: 遅延が「打った文字のエコー自体」なのか「一覧の更新」なのかは体感では区別できていない。前者なら「入力を決してブロックしない」原則(受け入れ条件 2「体感遅延なし」)の違反になるため、切り分けが必要。
- 仮説(備考): 「一覧をいったん消してから描き直す」更新モデルは、空白期間が遅延として可視化される点で、遅さの体感とチラつきの両方を生んでいる可能性がある。zsh-autocomplete は旧一覧を残したまま置き換えるため空白が見えない。
- 対処: 002-display-layer D1 の置き換え更新モデルで空白を排除。D5 の計測で
  打鍵パス上の恒常コスト(タイマー fork)は最大 0.4ms/打鍵と判明し仮説 b は棄却
  (計測記録は 002 plan.md)。体感遅延の解消を確認(2026-07-28)。

上記 5 件はすべて「使用をためらう」レベル(M5 完了条件に直接かかる)。ctrl+p/n を除く 4 件は `zle -M` 描画層に起因する共通根を持つ。制約(ANSI 不可・縦一列・見出しなし)に加え、全消し再描画という更新モデルがチラつきと遅延の体感を生んでおり、期待水準(背景色ハイライト・複数列グリッド・見出し付きグループ・空白の見えない更新)は個別の小修正では届かない。フェーズ 2 送りにしていた描画層差し替え(POSTDISPLAY + region_highlight)が M5 のブロッカーになっている、という発見。
描画層差し替え(遅延の切り分け含む)は `../002-display-layer/plan.md` で対応した。
ctrl+p/n の既定キーバインドは 002 のスコープ外とし、1 アクション複数キーのスキーマ拡張(keybind-multikey)で対応した。
→ 2026-07-28: 5 件すべて解消を体感確認。

### 2026-07-28 / mac — 一覧なし→初回表示までの「間」(コマンド名で顕著)

- 状況: 文字を打ってから一覧が最初に表示されるまでに一瞬の間を感じる。旧一覧が残っている間の追従の遅れは気にならない。コマンド位置(空語の全コマンド収集 = 最重量ケース)で顕著。
- 期待と実際: 期待は zsh-autocomplete 並みの初速。実際の打鍵→初回表示は「デバウンス 50ms + fork+compsys 収集(ファイル補完で実測 35ms、全コマンド収集はより重い)+ match 往復 ~5ms」で 100ms 超になり得る。旧 .zshrc の zsh-autocomplete も min-delay 0.05 だったため、デバウンス分は同条件で、差はデバウンス後の収集・描画にある。
- 切り分け方針: 実環境 ZRUSH_LOG での区間計測(pre-redraw → request → finalize → render)、`delay-ms = 0` でのデバウンス寄与の確認、zsh-autocomplete との同条件比較、zsh-autocomplete の収集方式(キャッシュ等)の調査。結果次第で収集アーキテクチャの見直し(キャッシュ・常駐化 = 001 plan スコープ外の布石)を検討する。
- 使用をためらうレベル(M5 完了条件に直接かかる)。

### 2026-07-28 / mac — Tab(common-prefix)が体感無反応(共通部分がほぼ出ない)

- 状況: コマンド入力中に Tab を押しても何も挿入されず、ctrl-n で選択に入って Tab 確定という手順になり面倒。config は `tab = "common-prefix"`。
- 期待と実際: 期待は zsh-autocomplete の `insert-unambiguous yes` + `complete-word` 相当(まず表示候補の共通部分を挿入、なければ先頭候補を挿入)。実際は共通接頭辞を**全マッチ候補**(typo・あいまい階層を含む)の LCP で計算し「クエリが LCP の真の接頭辞のときのみ挿入」のため、mode=typo では LCP がすぐ空になり無反応が常態化する(仕様どおりだが期待とずれ)。
- 対処方針(決定済み): (a) LCP の計算対象を絞る(表示中の上位のみ or prefix/substring 階層のみ — どちらにするかは設計時に決定)、(b) 共通部分がない・伸びないときは**先頭候補を挿入**するフォールバックを入れる。cli-protocol の common-prefix 仕様の変更を伴う。
- 使用をためらうレベル(M5 完了条件に直接かかる)。
- 対処: `../003-tab-common-prefix/plan.md` で実装(LCP は prefix 階層限定に確定、
  伸びなければ先頭候補を確定挿入。プロトコル v3)。体感確認待ち。
- 2026-07-29 追記: **フォールバック(先頭候補の確定挿入)に違和感**。`cla` + Tab で
  `clangd` が丸ごと挿入され、削除で戻すことが多い。保守的な挙動が望ましい。
  プロトコル検証で機序を確認: (i) `cla` の prefix 階層は分岐点にあり LCP == クエリ、
  さらに大小文字混在候補(ClassInitGenerator 等)が入るとバイト LCP は空に潰れる —
  いずれの経路でもフォールバックが発火する。(ii) `cd re` → `repos` は
  LCP が伸びるため cp 挿入側が働き快適。つまり 003 の (a) LCP 絞り込みは意図どおりで、
  違和感の源は (b) フォールバックのみ。なお「clang で止まる」は厳密な LCP では
  原理的に出ない(claude が cla 直後で分岐するため、保守的にできる最大は「何もしない」)。
  → 検討の結果、**現状維持で経過観察**(2026-07-29 決定)。削除で戻す頻度が実際に
  ストレスかで再判断する。代替案は「何もしない(撤去)」と「メニュー開始への変更」
  (後者は現状の手動フロー ctrl-n → Tab を Tab, Tab に縮めたものと等価)。
  cp 挿入側(cd re → repos 型)はどの案でも不変。

## 好み・チューニング候補

### 2026-07-28 / mac — グループ見出しが compsys の生ラベルのまま(「external command」等)

- 状況: コマンド位置の補完で見出しが「external command」と表示される。zsh-autocomplete では「command」だった。
- 期待と実際: 期待は zsh-autocomplete と同水準の簡潔な見出し。実際は compsys のタグ説明文(`%d`)を無加工で表示しており冗長。ほかにも意味のない微妙な差異がありそう。
- 対処方針: zsh-autocomplete の実際の見出しを列挙して差分を調査してから、リネーム(external command → command 等)で済ませるか、グループ統合(external / builtin / alias を 1 つの command 見出しへ等)まで踏み込むかを決める。期待水準は調査結果で確定させる仮置き。

### 2026-07-28 / mac — グリッド端の選択移動がラップしない

- 状況: 6 列 × 2 行の一覧で、0 始まり座標 (x, y)・右上 = (5,0) のとき、↑ で (4,1)(表示順 −1)、→ で (5,1)(列ジャンプの端クランプ)へ移動する。
- 期待と実際: 期待は軸ごとのラップ(トーラス): (5,0) の ↑ は同列下端 (5,1)、→ は同行左端 (0,0)。実際は「表示順の 1 次元 ±1 + 左右は列ジャンプ・端クランプ」。
- 備考: 好みが分かれる領域なので、移動則をモデル化して設定可能にする方向(例: `selection-wrap = "linear" | "axis"`)。ただし「上端の ↑ = 選択解除(履歴への導線)」との整合(解除に残す方が筋がよい可能性)、端数列(歯抜けの最終列)やグループ跨ぎでのラップ先の定義は未決で、UI/UX を含めて改めて設計する。
