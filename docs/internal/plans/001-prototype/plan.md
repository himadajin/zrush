# 001-prototype 実装計画

## 背景と目的

現行の marlonrichert/zsh-autocomplete には、頻繁な破壊的変更・細部動作の不安定さ・設定不能な挙動(`~` の勝手な展開、Tab での過剰な補完挿入、あいまい入力が補完されない、キーバインド設定不可)への不満がある。これを置き換える自分専用ツール zrush を作る。

元アイディアのドキュメントは [`idea/`](idea/)([design.md](idea/design.md) / [config.md](idea/config.md))にある。

このプランのゴールは、元アイディア([idea/design.md](idea/design.md))のフェーズ 1 に相当する **日常投入可能な最小形** を完成させること:

- リアルタイム候補一覧(入力に追従してプロンプト下に自動表示)
- あいまいマッチ(前方一致/部分一致/誤字許容)
- `config.toml` による設定(表示・マッチング・挿入確定・キーバインド)
- 候補一覧からの簡易選択(上下移動 + 確定/却下)

環境: macOS (arm64, zsh 5.9) を主環境とし、**Linux(SSH 先のサーバ / WSL / コンテナ)でも使う**。最低サポート zsh バージョンは **5.8**(必要機能の `zle -F -w` は 5.4+、`zle-line-pre-redraw` は 5.3+ で、主要ディストリの zsh をカバーできる下限)。第三者への配布は非目標。

## 決定事項

| 項目 | 決定 | 補足 |
|---|---|---|
| スコープ | フェーズ 1 相当を日常投入品質で作る | 使い捨てスパイクにはしない |
| 候補の非同期収集 | **zpty 方式** を本命 | zpty 内で現在シェルの fork として内部シェルを起動し、compsys を走らせて候補を吸い出す。部分的な前例は zsh-autosuggestions の completion strategy / zsh-capture-completion(いずれも単一候補向け)。**複数候補+メタデータの一覧取得は未踏**であり、これが最大の技術リスク |
| 収集のフォールバック | **同期収集+デバウンス** | zpty 方式が成立しない場合は、fzf-tab 型の「現在シェル内で compadd を関数差し替えして同期収集し、デバウンスで体感非同期化」に切り替える。compsys は zle の補完ウィジェット文脈でしか呼べないため、pty なしのバックグラウンド子シェルはフォールバックにならない |
| 候補一覧の描画 | **`zle -M`** | 最も安全でプロンプト位置を乱さない。描画層は後で差し替え可能な構造にする。選択中候補はマーカー(`> ` 接頭辞)で示す(`zle -M` 内の ANSI エスケープは幅計算に入らず崩れるため使わない) |
| マッチ箇所ハイライト | フェーズ 1 では**設定項目に含めない** | `zle -M` では実現できないため。POSTDISPLAY + region_highlight へ描画層を差し替えるときに設定ごと導入する(idea/config.md からの意図的な差分) |
| 候補一覧の操作 | 簡易選択まで含める | 上下キーで候補を選び Enter/Tab で確定。本格的な Tab メニュー選択・履歴メニューはフェーズ 2 |
| あいまいマッチ実装 | 既存クレート活用 | fuzzy 部分は実績あるクレート(候補: `nucleo-matcher`)、誤字許容は必要に応じて自前ロジックで補完 |
| プロセスモデル | 常駐デーモンなし | キー入力ごとに Rust CLI を都度起動。小バイナリの spawn は実測 1.4ms、5000 行のパイプ I/O 込みでも 2.5ms 程度であり、`zrush match` 一往復は 5ms 前後に収まる見込み。リリースビルドで使うこと |
| キーバインドの責務分担 | Rust は記法の正規化、端末依存キーは zsh が解決 | `"ctrl-n"` → `^N` のような自明な変換は Rust。`up` / `shift-tab` など端末依存キーは Rust がシンボリック名のまま出力し、zsh 側が `$terminfo` を参照して解決する(矢印は CSI/SS3 両系統を bindkey)。端末状態は zsh 側にしか見えないため |
| Linux 対応 | フェーズ 1 のスコープに含める([idea/design.md](idea/design.md) の「非目標」からの意図的な差分) | 実際に SSH 先サーバ / WSL / コンテナで使うため。CI(Linux + macOS)は M2 から、実機での統合確認・ドッグフーディングは M5 で行う。バイナリは各環境で `cargo build` する(クロスコンパイル・配布はしない) |
| 移植性ガードレール | mac 固有依存を作らない | zsh スクリプトから呼ぶ外部コマンドは POSIX 範囲のみ(現状 `sleep` / `stty` を想定)。config パスは `$XDG_CONFIG_HOME` → `~/.config` の解決を自前実装(OS のプラットフォーム慣習パスに寄せない)。Rust はプラットフォーム固有 API 禁止。zsh 5.8 に存在しない機能を使わない |

元アイディアからの引き継ぎ決定([idea/design.md](idea/design.md) / [idea/config.md](idea/config.md) 由来):

- 「勝手に何かをしない」原則はコードに固定し、設定項目にしない(`~` 非展開、明示操作なしの書き換え禁止)。
- 設定は `~/.config/zrush/config.toml`(XDG 準拠)に一元化。zstyle 面は作らない。
- 既定値: 一覧 10 行、表示遅延 50ms、min-input 0。`config.toml` が存在しない場合は全既定値で動作する。
- 設定はプロンプト表示ごとに mtime を確認して自動反映。明示のリロードコマンドは不要。
- 不正な設定値でも起動は止めず、該当項目を既定値にフォールバックし、その旨が分かるエラー表示を出す。
- コマンド別オーバーライドはフェーズ 2 検討事項。

## アーキテクチャ

```
┌─ zsh (zsh/zrush.zsh) ────────────────────────────────┐
│ zle 統合                                              │
│  ├ zle-line-pre-redraw でバッファ変化を検知           │
│  ├ fd タイマーで表示遅延(デバウンス)                │
│  ├ zpty 内部シェル(現在シェルの fork)で compsys を  │
│  │  実行し候補を収集、完了を zle -F -w で検知         │
│  ├ 状態依存ディスパッチ(一覧表示中のみ選択キーが有効)│
│  └ zle -M で候補一覧を描画                            │
└──────────┬───────────────────────────────────────────┘
           │ 都度起動 (stdin/stdout, NUL 区切り)
┌──────────▼───────────────────────────────────────────┐
│ Rust CLI: zrush                                       │
│  ├ zrush match   … 候補列+クエリ → マッチ・ランキング  │
│  ├ zrush config  … config.toml → zsh が source できる  │
│  │                 設定値・bindkey 定義を出力           │
│  └ (内部) config パース / fuzzy / ランキング / キー変換 │
└──────────────────────────────────────────────────────┘
```

- **zsh 側の責務**: zle 統合、compsys 呼び出し(zpty)、描画、キーバインドの適用、端末依存キーの解決。
- **Rust 側の責務**: あいまいマッチング、ランキング、`config.toml` の解釈、キーバインド記法の正規化。

zle 統合の設計上の要点:

- **バッファ変化の検知は `zle-line-pre-redraw`** で行う(前回の `BUFFER`/`CURSOR` との差分検知)。self-insert のラップでは貼り付け・undo・kill 系・履歴移動などの変化を取りこぼす。
- **表示遅延(デバウンス)は fd タイマー**で実現する: バックグラウンドの `sleep` 子プロセス+パイプの fd を `zle -F` で監視する。zle 自体にタイマー機構はない。キー連打時はタイマーを作り直す。
- **候補収集は zpty をリクエストごとに作り直す**。新しい入力が来たら旧 zpty を `zpty -d` で破棄し(キャンセル)、世代番号で遅延して届いた stale な結果を捨てる。シェル終了時にも `zshexit` で破棄する。
- **収集完了の検知・描画は `zle -F -w`** で行う(ハンドラをウィジェットとして実行させ、`BUFFER` 参照と `zle -M` 描画を可能にする)。`zrush match` の呼び出しはこのハンドラ内(収集完了後)に置き、キー入力パスには置かない。
- **選択キーは状態依存ディスパッチ**にする: up/down/Enter/Tab は「一覧表示中」のみ zrush のアクションとして扱い、非表示時は既定のウィジェット(`.up-line-or-history` 等)へフォールバックするディスパッチウィジェットを bindkey する。
- 内部シェルには zrush 自身のフックが fork で継承されるため、**環境変数ガード(例: `ZRUSH_INTERNAL=1`)で再帰を防止**する。
- zsh↔Rust の入出力仕様は `docs/internal/contracts/cli-protocol.md` として M2 で確定させる(候補は NUL 区切りで stdin、クエリ・文脈は引数、出力はランク済み候補列、を想定。ファイル名は改行を含み得るため NUL 区切りは必須)。

## マイルストーン

リスクの大きい順に潰す([idea/design.md](idea/design.md) の「非同期収集という最大の技術リスクを最初に潰す」に従う)。

### M1: zpty による compsys 候補収集の技術検証(最大リスク)

zpty 内部シェル(現在シェルの fork)で compsys を走らせ、編集バッファに対する補完候補を吸い出す zsh スクリプトを書く。参照実装: zsh-autosuggestions の completion strategy(zpty + `vared` + NUL 番兵)、fzf-tab の `-ftb-compadd`(compadd 差し替え)。

検証項目:

- **候補の正しさ**: ファイル名 / コマンド名 / git サブコマンド / オプションの各補完で候補が取れる。
- **compadd フックの網羅性**: 説明文(`-d`)とグループ(`-J`/`-V`/`-X`)の取得、`-O`/`-A` 付き呼び出し(マッチテスト用)を候補として数えない、接頭辞・接尾辞(`-P`/`-S`/`-p`/`-s`/`-i`/`-I`)込みの挿入文字列の再構成、表示文字列と挿入文字列の区別。
- **pty 出力の清浄化**: `stty -onlcr` 等の設定、NUL 番兵による結果のフレーミング、`zpty -b` + `zle -F` での部分読みの再組み立て、改行を含むファイル名の往復。
- **キャンセルと後始末**: リクエストごとの zpty 作り直し+`zpty -d` によるキャンセル、世代番号による stale 結果の破棄、`zshexit` での掃除、再帰防止ガードの動作。
- **計測**: 1 リクエストの端到端レイテンシ(fork〜候補受信完了)、大量候補(数千件)での入力非ブロック、連打時の挙動。
- `~` を含む入力が展開されずに扱えること。

成立しない場合はフォールバック(同期収集+デバウンス)に切り替え、この plan を更新する。

成果: 検証用スクリプトと、収集方式の結論・計測値を `notes-zpty.md`(このディレクトリ)に記録。

### M2: Rust コア

- `cargo init`。`zrush match` / `zrush config` サブコマンドの骨組み。
- `config.toml` パース: 表示(max-lines / delay-ms / min-input)、マッチング(強度: prefix / substring / typo、smart-case)、挿入・確定(Tab 挙動、末尾スペース)、キーバインド。不正値は既定値フォールバック+警告。config 不在時は全既定値で動作。
- マッチング: `nucleo-matcher` を評価して採用可否を決め、前方一致/部分一致/誤字許容の 3 モード+smart-case とランキングを実装。
- キーバインド記法の正規化(`"ctrl-n"` → `^N`、端末依存キーはシンボリック名のまま出力)。デフォルトキーバインド一覧もここで確定する(却下キーの既定は Escape でなく `ctrl-g` を第一候補とする — Escape 単独は矢印キー等の `\e` プレフィックスと曖昧で KEYTIMEOUT 待ちが発生するため。最終決定はここで行う)。
- ここまでを純粋ロジックとして単体テストを整備。
- CI を整備: GitHub Actions で Linux (ubuntu) + macOS の `cargo build` / `cargo test` を回す。
- 成果: `docs/internal/contracts/cli-protocol.md`(zsh↔Rust プロトコル)と `docs/internal/contracts/config-schema.md`(config.toml のテーブル・キー・型・既定値の一覧。設定エラーの表示先・タイミングを含む)を作成。以後この 2 つを真実とし、コードを追従させる。

### M3: 統合 — リアルタイム候補一覧

- `zle-line-pre-redraw` でのバッファ変化検知 → fd タイマーで遅延(既定 50ms)→ M1 の方式で候補収集 → `zle -F -w` ハンドラ内で `zrush match` → `zle -M` で一覧描画、を通す。
- min-input・max-lines を config から適用。各行は `$COLUMNS` 未満に切り詰め(折り返しによる行数暴れの防止)、行数は max-lines と `$LINES` の小さい方でクリップ。
- `zle-line-finish` で `zle -M ""` により一覧を消去(accept-line 後の残骸防止)。
- 端末リサイズ時の挙動を確認。
- 完了判定: 検証用起動スクリプト上で受け入れ条件 2 相当(一覧の自動表示+大量候補での非ブロック)が確認できる状態。

### M4: 選択・確定・挿入

- 状態依存ディスパッチウィジェットを実装し、一覧表示中のみ上下キーで候補選択、Enter/Tab で確定、却下キーで閉じる(キーはすべて config のキーバインド定義から適用)。選択中候補はマーカーで表示する。
- Tab の挙動を config で制御(共通接頭辞のみ挿入 / メニューへ入るだけ / 即挿入)。
- 確定時の末尾スペース付与の有無を config で制御。
- `~/` 配下の候補を確定しても `~` が展開形に置き換わらないことを確認(compadd の接頭辞経由の再構成で壊さない)。

### M5: 日常投入と仕上げ

- 設定の mtime 自動反映(プロンプト表示ごとに確認し、bindkey を再適用)。
- 設定エラー時のフォールバック表示(仕様は config-schema.md に従う)。
- zsh-autocomplete を無効化し zrush に切り替えて日常利用開始。気になった挙動をこのディレクトリの `notes-dogfooding.md` に記録し、チューニング。チェックリストには通常操作に加えて、端末リサイズ・複数行バッファ(継続行)・tmux 内・accept-line 後の残骸・シェル多重起動を含める。
- Linux 実機検証: 実際に使う Linux 環境(SSH 先サーバ / WSL / コンテナ)に導入し、検証用スクリプトで受け入れ条件 2〜7 を確認したうえでドッグフーディングに含める。zsh 5.8 環境が含まれる場合はそこでの動作確認を最低サポートの根拠とする。
- 完了判定: 2 週間の日常利用(mac + Linux)で「使用をためらう問題」が `notes-dogfooding.md` 上でゼロになったら、確定仕様を `docs/internal/specs/`(挙動仕様・config スキーマ)へ昇格し、`docs/user/` に導入・設定ドキュメントを作成して完了。

## 受け入れ条件

[idea/design.md](idea/design.md) の完了条件をベースに、簡易選択と検証可能性の具体化を加えたもの:

1. zsh-autocomplete を無効化し、zrush だけで日常のシェル操作ができる(M5 のドッグフーディングで判定。最低限: cd のパス補完・git サブコマンド補完・コマンドオプション補完・ファイル名補完が各々日常頻度で成功する)。
2. 入力中、候補一覧がプロンプト下に自動表示され、数千件の候補でも入力がブロックされない(取りこぼし・体感遅延なし)。
3. `~` を含む入力が、入力中も候補確定時も勝手に展開されない。
4. あいまいな入力でも目的の候補に到達できる(例: `gti`→`git` のような転置タイプミス、`dcs`→`docs` のような部分文字一致で候補が出る)。
5. 候補一覧から上下キーで候補を選び、確定・却下できる。
6. フェーズ 1 の全設定項目(max-lines / delay-ms / min-input / マッチ強度 / smart-case / Tab 挙動 / 末尾スペース / 全キーバインド)が `config.toml` で変更でき、次のプロンプトから自動反映される。
7. 不正な設定値でも起動が止まらず、既定値フォールバックが分かるエラー表示になる。
8. Rust 側のマッチング・ランキング・設定パース・キー変換に単体テストが存在し、通っている(CI で Linux + macOS の両方が通る)。
9. 実際に使う Linux 環境(SSH 先サーバ / WSL / コンテナのうち少なくとも 1 つ、可能なら zsh 5.8 環境を含む)で受け入れ条件 2〜7 が成立する。

## 検証方法

- **Rust コア**: `cargo test`(マッチング・ランキング・config パース・キー変換の単体テスト)。GitHub Actions で Linux + macOS の両方を回す。受け入れ条件 8。
- **zsh 統合**: `zsh -f` から zrush だけを読み込む検証用起動スクリプトを `zsh/` に用意し、受け入れ条件 2〜7 をチェックリストとして確認する。非ブロック性(条件 2)は候補数千件のディレクトリを生成して連続タイプで確認。同じスクリプトを Linux 実機でも実行する(受け入れ条件 9)。
- **日常投入**: 受け入れ条件 1 は M5 のドッグフーディング(`notes-dogfooding.md`)で判定する。

## 未解決事項(実装中に判断)

- zpty 内部シェル初期化の詳細(fork 時点の状態で十分か、追加の初期化が要るか)— M1 で決定し `notes-zpty.md` に記録。
- 誤字許容マッチの具体アルゴリズム(nucleo-matcher で足りるか、編集距離ベースの補完が要るか)— M2 で決定。
- `zle -M` で表示できる情報量の限界(説明文・グループの見せ方)— M3/M4 で決定。不足なら POSTDISPLAY + region_highlight 方式への差し替えを検討(その際にマッチ箇所ハイライト設定も導入する)。
