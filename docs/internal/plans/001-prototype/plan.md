# 001-prototype 実装計画

## 背景と目的

marlonrichert/zsh-autocomplete のリアルタイム補完体験を気に入って使ってきたが、日常利用の中で、挙動を細部まで自分の手で決めたい場面が増えてきた。
そこで、同種の体験を提供するツール zrush を作り、これを置き換える。
開発は作者の日常利用を第一とし(ドッグフーディング駆動)、挙動の優先順位や品質判断はそこを基準にする。

zrush で解決したいこと:

- 明示操作なしに入力が書き換わらないこと(例: `~` が展開されない)。
- Tab で何がどこまで挿入されるかを自分で決められること。
- あいまい入力(typo)からでも目的の候補に到達できること。
- キーバインドを設定できること。
- 挙動が上流の変更に左右されず、自分のペースで固定・安定させられること。

zrush の最終ゴールは、リアルタイム候補一覧・履歴メニュー/絞り込み・Tab メニュー選択・あいまい(誤字許容)マッチを備え、全挙動を `config.toml` で制御でき、上流依存なしで安定して日常利用できる状態。
段階導入とし、このプラン(フェーズ 1)のゴールはその **日常投入可能な最小形** を完成させること:

- リアルタイム候補一覧(入力に追従してプロンプト下に自動表示)
- あいまいマッチ(前方一致/部分一致/誤字許容)
- `config.toml` による設定(表示・マッチング・挿入確定・キーバインド)
- 候補一覧からの簡易選択(上下移動 + 確定/却下)

環境: macOS (arm64, zsh 5.9) を主環境とし、**Linux(SSH 先のサーバ / WSL / コンテナ)でも使う**。
最低サポート zsh バージョンは **5.8**(必要機能の `zle -F -w` は 5.4+、`zle-line-pre-redraw` は 5.3+ で、主要ディストリの zsh をカバーできる下限)。
第三者向けの配布・サポートはフェーズ 1 のスコープ外(将来のリリースは妨げない)。
速度要件: zsh-autocomplete と同等以上でよい(現状の速度に体感の不満はない)。
ただし入力は決してブロックしないこと。

## 決定事項

- **スコープ** — フェーズ 1 相当を日常投入品質で作る
  - 使い捨てスパイクにはしない。
- **候補の非同期収集** — **zpty 方式**を本命
  - zpty 内で現在シェルの fork として内部シェルを起動し、compsys を走らせて候補を吸い出す。
  - 部分的な前例は zsh-autosuggestions の completion strategy / zsh-capture-completion(いずれも単一候補向け)。
  - **複数候補+メタデータの一覧取得は未踏**であり、これが最大の技術リスク。
- **収集のフォールバック** — 事前コミットしない
  - zpty 方式が成立しなかった場合は、失敗原因(pty 出力の清浄化・レイテンシ・メタデータ搬出など)を踏まえて選び直し、この plan を更新する。
  - 候補と、各々が諦めるもの:
    - 同期収集+デバウンス(fzf-tab 型の compadd 差し替えを現在シェルで実行)—「入力を決してブロックしない」原則を諦める(遅い補完関数で対話シェルが固まる)。
    - fish 型(リアルタイム一覧は glob・コマンド名・履歴など安価な自前ソースのみ、compsys は Tab 時のみ同期実行)— compsys 候補のリアルタイム表示を諦める。
  - compsys は zle の補完ウィジェット文脈でしか呼べないため、pty なしのバックグラウンド子シェルはフォールバックにならない。
- **あいまいマッチの実現層** — compsys ではなく Rust で行う
  - compsys は入力語で前方一致フィルタをかけるため、as-typed のまま収集すると `gti` のようなあいまい入力では候補が空になる。
    そこで収集時はクエリを広げて候補全集合を取り、実際の入力語は Rust 側の fuzzy クエリとしてのみ使う。
  - matcher-list / `_approximate` で compsys 側にあいまい化を担わせる案は採らない
    (zsh-autocomplete と同方式で、挙動を自分の手で制御したいという本プロジェクトの動機に合わない。ランキングの制御もしにくい)。
  - compsys 固有の複数セグメント略記(`/u/l/b` → `/usr/local/bin`)は失われる。
    ドッグフーディングで必要になったら as-typed 併用収集(フェーズ 2)で取り戻す。
- **収集クエリの広げ方** — セグメント保持規則
  - 現在語(カーソルまで)のうち、最後の `/` または `=` より後ろを空にして収集する。
    区切りがなく `-` で始まる語は先頭のダッシュ列を保持する。
    それ以外は語全体を空にする。
  - 削った末尾が Rust に渡す fuzzy クエリになる。
    規則は zsh 側の文字列操作で実装する。
- **確定時の置換範囲** — 原則は広げ規則で削った末尾領域、接頭辞不一致時のみ現在語全体
  - 確定は「削った領域を、候補の挿入文字列(compadd の `-P`/`-S` 等を再構成したもの)で置き換える」操作とする。
  - ただし補完関数が語頭の保持部分を書き換えた形で候補を返すケースがある(部分パス略記 `pp/u/lo` では接頭辞が `pp/usr/` に展開されて返る)。
    そこで、候補の捕獲接頭辞(IPREFIX + hpre)が保持したバッファ末尾と一致する場合は末尾領域のみを置換し、
    不一致の場合は置換範囲を現在語全体に拡張する(M1 で全検証ケースについて素の compsys の実挿入との一致を確認済み)。
  - `~/` は補完関数から未展開のまま返るため常に末尾置換側となり、`~` 非展開はこのモデルで引き続き保証される(M1 実証)。
  - カーソル以降のテキストには触らない(「勝手に何かをしない」原則の帰結)。
  - compsys の語範囲メタデータ(IPREFIX/ISUFFIX 等)は候補レコードの一部として zpty から持ち帰り、上記の一致判定に使う
    (M1 で捕獲・搬出とも実証済み。広げ規則との二重管理を避けるため、置換範囲の決定はあくまで zsh 側の広げ規則+一致判定で行う)。
- **候補一覧の描画** — **POSTDISPLAY + region_highlight**
  (当初の `zle -M` は M5 ドッグフーディングの指摘を受けて差し替えた。
  設計・経緯は `../002-display-layer/plan.md`)
  - 更新は POSTDISPLAY の置き換え(旧一覧を残したまま差し替え、空白を見せない)。
  - 表示は列優先グリッド+グループ見出し。選択セルは standout 系ハイライトで示す
    (レイアウトは動かない)。
- **マッチ箇所ハイライト** — `[display.highlight]` で設定可能(002 で導入。
  既定は selected=standout / match=underline / heading=bold)
- **候補一覧の操作** — 簡易選択まで含める
  - キーの特別扱いは「一覧表示中」ではなく「**選択中**」に限る。
    min-input 0 では一覧がほぼ常時表示されるため、表示中を条件にすると Enter での実行や ↑ での履歴移動が奪われてしまう。
  - 非選択時は zsh 既定のまま(↑=履歴、Enter=実行)。
    ↓ で選択に入り、選択中のみ ↑↓=候補移動、Enter/Tab=確定、却下キーで閉じる。
    先頭候補での ↑ は選択解除して通常状態に戻る(履歴への導線を残す)。
  - 非選択時の ↓ は優先順位規則で解決する(コードに固定し、設定項目にしない):
    ① 複数行バッファの途中行にカーソルがある → カーソル移動、
    ② 履歴移動中(`HISTNO` が末尾でない) → 履歴戻り、
    ③ 一覧表示中 → 選択開始、
    ④ それ以外 → 既定ウィジェット。
    判定はすべて zsh 変数(`BUFFER`/`CURSOR`/`HISTNO`)の参照のみで行える。
  - 候補未着時(収集中・デバウンス待ち)の Tab は、収集完了を待って挙動を適用する:
    Tab 押下を記録し、デバウンスタイマーを即発火させて収集を前倒しし、結果到着時に `[insert]` の設定どおりに動く。
    候補 0 件なら何もしない。
    素の compsys への同期フォールバックはしない(対話シェルでの同期実行になり、前方一致のみ・ネイティブ UI 混入で挙動も食い違うため)。
  - 確定は挿入のみで、コマンドは実行しない(実行はもう一度 Enter)。
    「勝手に何かをしない」原則の帰結としてコードに固定し、設定項目にしない。
  - 本格的な Tab メニュー選択・履歴メニューはフェーズ 2。
- **空バッファでは何もしない** — 収集も表示もしない(固定挙動、設定項目にしない)
  - プロンプト直後の 0 文字状態では、全コマンド名(数千〜数万件)という最重量の収集が走るだけで一覧はノイズにしかならないため。
    min-input 0 は `cd ` 直後のような空の引数語では有効のまま。
  - フェーズ 2 の履歴メニュー導入時に、空バッファの意味をあらためて定義し直す。
- **候補数の上限は設けない** — M1 で実測してから判断
  - 非ブロック保証は zpty の非同期性によるもので、収集が遅くても「一覧が遅れて出る」だけ。
    上限は正しさではなく最適化の問題なので、実測で必要と分かったときに打ち切り(+truncated 表示)を導入する。
  - Rust → zsh の出力は上位 max-lines 件のみ(プロトコルに明記)。
- **あいまいマッチ実装** — 既存クレート活用
  - fuzzy 部分は実績あるクレート(候補: `nucleo-matcher`)、誤字許容は必要に応じて自前ロジックで補完。
- **プロセスモデル** — 常駐デーモンなし
  - キー入力ごとに Rust CLI を都度起動。
  - 小バイナリの spawn は実測 1.4ms、5000 行のパイプ I/O 込みでも 2.5ms 程度であり、`zrush match` 一往復は 5ms 前後に収まる見込み。
  - リリースビルドで使うこと。
- **キーバインドの責務分担** — Rust は記法の正規化、端末依存キーは zsh が解決
  - `"ctrl-n"` → `^N` のような自明な変換は Rust。
  - `up` / `shift-tab` など端末依存キーは Rust がシンボリック名のまま出力し、zsh 側が `$terminfo` を参照して解決する(矢印は CSI/SS3 両系統を bindkey)。
  - 端末状態は zsh 側にしか見えないため。
- **プラグイン共存** — 汎用メカニズム 2 つで対応し、検証は作者環境のみ
  - キーのフォールバック先は builtin 直呼び(`.accept-line` 等)ではなく、**zrush 適用前にそのキーに束縛されていたウィジェットへの前任者チェーン**とする
    (builtin 直呼びだと zsh-abbr の Enter ラップが素通しされ、略語展開が壊れる)。
    config リロードでの bindkey 再適用時に、自分自身を前任者として捕まえないこと。
  - `zle-line-pre-redraw` は自前定義ではなく `add-zle-hook-widget` 経由で登録する(同フックを使う zsh-syntax-highlighting と共存するための公式メカニズム)。
  - 検証対象は実際に使う zsh-syntax-highlighting と zsh-abbr の 2 つのみ。
    **一般のプラグイン互換性はフェーズ 1 では保証しない**(検証は作者環境を基準とする)。
- **Linux 対応** — フェーズ 1 のスコープに含める
  - 実際に SSH 先サーバ / WSL / コンテナで使うため。
  - CI(Linux + macOS)は M2 から、実機での統合確認・ドッグフーディングは M5 で行う。
  - バイナリは各環境で `cargo build` する(クロスコンパイル・バイナリ配布はフェーズ 1 のスコープ外)。
- **移植性ガードレール** — mac 固有依存を作らない
  - zsh スクリプトから呼ぶ外部コマンドは POSIX 範囲のみ(現状 `mkfifo` / `rm`。
    デバウンスは `zselect`、搬出 pipe は fifo の匿名化で実現しており `sleep` / `stty` は不要になった)。
  - config パスは `$XDG_CONFIG_HOME` → `~/.config` の解決を自前実装(OS のプラットフォーム慣習パスに寄せない)。
  - Rust は特定 OS 固有の API を禁止する(mac / Linux の両方で使えない依存を作らない)。
    両対応の unix 共通 API(例: `std::os::unix::ffi::OsStrExt` による argv の生バイト受理)は許容する。
  - zsh 5.8 に存在しない機能を使わない。
- **導入形態** — clone → `cargo build --release` → `.zshrc` で source
  - zrush.zsh は自身の位置(`${0:A:h}`)から `../target/release/zrush` を解決する。
    `$ZRUSH_BIN` が設定されていればそちらを優先。
    `cargo install` や PATH 配置を前提にしない(rebuild が即反映され、ドッグフーディング向き)。
  - compsys が初期化済み(compinit 実行済み)であることを動作前提とし、source は compinit より後に置く。
    zrush 自身は compinit を実行しない(「勝手に何かをしない」)。
    未初期化を検知したら警告表示のみ行う。
- **zsh スクリプトとバイナリの版不整合** — プロトコル版番号で警告
  - cli-protocol.md にプロトコル版番号を含め、zrush.zsh が期待する版と `zrush config` が出力する版が不一致なら警告を 1 回表示する(動作は継続)。
  - 複数環境で使うため、git pull 後の rebuild し忘れが原因不明のデバッグに化けるのを安価に防ぐ。

設定・原則まわりの決定:

- 「勝手に何かをしない」原則はコードに固定し、設定項目にしない(`~` 非展開、明示操作なしの書き換え禁止)。
- 設定は `~/.config/zrush/config.toml`(XDG 準拠)に一元化。
  zstyle 面は作らない。
- 既定値: 一覧 10 行、表示遅延 30ms、min-input 0。
  `config.toml` が存在しない場合は全既定値で動作する。
- 設定はプロンプト表示ごとに mtime を確認して自動反映。
  明示のリロードコマンドは不要。
- 不正な設定値でも起動は止めず、該当項目を既定値にフォールバックし、その旨が分かるエラー表示を出す。
- 設定項目を増やしすぎない。
  原則系は固定という方針のとおり、調整する見込みの薄い項目はまず固定値で入れ、必要になってから設定化する。

## スコープ外(フェーズ 2 以降)

このプランでは作らない。
実利用で必要性が見えたときに次のプランで検討する:

- 履歴メニュー/絞り込み(並び順・重複除去・絞り込み対象〔先頭一致/全文〕の設定カテゴリを含む)と、それに伴う Rust 側の履歴検索。
  空バッファの意味の再定義(フェーズ 1 では空バッファで何もしない)もこのとき行う。
- as-typed 収集の併用(compsys の複数セグメント略記 `/u/l/b` → `/usr/local/bin` の復活)。
  広げた収集に as-typed 収集を追加しマージする形なので、フェーズ 1 の方式からの手戻りにはならない。
- 本格的な Tab メニュー選択。
- コマンド別オーバーライド(例: git のときだけ一覧行数を変える)。
- 常駐デーモン(都度起動で速度不足が実測されたときの後続手段)。

## アーキテクチャ

```
┌─ zsh (zsh/zrush.zsh) ────────────────────────────────┐
│ zle 統合                                              │
│  ├ zle-line-pre-redraw でバッファ変化を検知           │
│  ├ fd タイマーで表示遅延(デバウンス)                │
│  ├ zpty 内部シェル(現在シェルの fork)で compsys を  │
│  │  実行し候補を収集、完了を zle -F -w で検知         │
│  ├ 状態依存ディスパッチ(状態・キー別に分岐)          │
│  └ POSTDISPLAY + region_highlight で候補一覧を描画    │
└──────────┬───────────────────────────────────────────┘
           │ 都度起動 (stdin/stdout, NUL 区切り)
┌──────────▼───────────────────────────────────────────┐
│ Rust CLI: zrush                                       │
│  ├ zrush match   … 候補列+クエリ → マッチ・ランキング  │
│  ├ zrush config  … config.toml → zsh が source できる  │
│  │                 設定値・bindkey 定義を出力           │
│  └ (内部) config パース / fuzzy / ランキング / キー変換 │
└──────────────────────────────────────────────────────┘
```

- **zsh 側の責務**: zle 統合、compsys 呼び出し(zpty)、描画、キーバインドの適用、端末依存キーの解決。
- **Rust 側の責務**: あいまいマッチング、ランキング、`config.toml` の解釈、キーバインド記法の正規化。

zle 統合の設計上の要点:

- **バッファ変化の検知は `zle-line-pre-redraw`** で行う(前回の `BUFFER`/`CURSOR` との差分検知)。
  self-insert のラップでは貼り付け・undo・kill 系・履歴移動などの変化を取りこぼす。
  登録は `add-zle-hook-widget` 経由(プラグイン共存の決定を参照)。
- **表示遅延(デバウンス)は fd タイマー**で実現する:
  プロセス置換内の `zselect -t` が期限後に出力する pipe の fd を `zle -F` で監視する。
  zle 自体にタイマー機構はない。
  キー連打時はタイマーを作り直す。
- **候補収集は zpty をリクエストごとに作り直す**。
  新しい入力が来たら旧 zpty を `zpty -d` で破棄し(キャンセル)、世代番号で遅延して届いた stale な結果を捨てる。
  シェル終了時にも `zshexit` で破棄する。
- **収集完了の検知・描画は `zle -F -w`** で行う(ハンドラをウィジェットとして実行させ、
  `BUFFER` 参照と POSTDISPLAY / region_highlight の更新を可能にする。
  ハンドラからの表示反映には `zle -R` が必要)。
  `zrush match` の呼び出しはこのハンドラ内(収集完了後)に置き、キー入力パスには置かない。
- **選択キーは状態依存ディスパッチ**にする:
  選択中は候補移動・確定として扱い、非選択時は ↓ が優先順位規則に従って一覧から選択を開始する。
  却下キーは一覧表示中にも一覧を閉じ、それ以外は前任者チェーンで zrush 適用前の
  ウィジェットへフォールバックする(builtin 直呼びはしない)。
  Tab は選択中なら確定し、非選択時は候補の到着状態と `[insert].tab` に従う。
- 内部シェルには zrush 自身のフックが fork で継承されるため、**環境変数ガード(例: `ZRUSH_INTERNAL=1`)で再帰を防止**する。
- zsh↔Rust の入出力仕様は `docs/internal/contracts/cli-protocol.md` として M2 で確定させる(候補は NUL 区切りで stdin、fuzzy クエリとマッチング設定は引数、出力はランク済み候補列の上位 max-lines 件、を想定。ファイル名は改行を含み得るため NUL 区切りは必須)。
  `zrush match` は config.toml を読まない純関数とする:
  設定はプロンプト表示時に zsh が `zrush config` で取得したスナップショットを引数で渡す(反映タイミングが「プロンプト表示ごと」に単一化され、mtime 確認も zsh 側の一箇所になる)。

## 導入方法(想定)

各環境(mac / SSH 先サーバ / WSL / コンテナ)で:

```sh
git clone <repo> ~/repos/zrush
cd ~/repos/zrush && cargo build --release
```

```sh
# .zshrc(zsh-autocomplete の source 行は削除する)
autoload -Uz compinit && compinit
source ~/repos/zrush/zsh/zrush.zsh
```

source 順: zsh-abbr より後(前任者チェーンが zsh-abbr のキー束縛を捕まえるため)、zsh-syntax-highlighting より前(z-sy-h は末尾配置が前提のため)。

`~/.config/zrush/config.toml` は任意(不在なら全既定値で動作)。
更新は git pull → 再ビルド。

## config.toml の絵姿(例)

スキーマの確定は M2(config-schema.md)で行う。
以下は設定面の全体像を共有するための例示:

```toml
[display]
max-lines = 10   # 一覧の最大行数
delay-ms  = 30   # 表示までの遅延
min-input = 0    # 表示を開始する最小入力文字数

[matching]
mode       = "typo"   # "prefix" | "substring" | "typo"(後のものほど広く拾う)
smart-case = true

[insert]
tab            = "menu"   # Tab の挙動: "common-prefix" | "menu" | "insert"
trailing-space = true     # 確定時の末尾スペース付与

[display.highlight]
selected = "standout"     # 選択セル
match    = "underline"    # マッチ箇所
heading  = "bold"         # グループ見出し

[keybind]                            # 1 アクション複数キー(文字列 / 配列)
select-next  = ["down", "ctrl-n"]    # 選択開始 / 次候補
select-prev  = ["up", "ctrl-p"]      # 前候補(先頭では選択解除)
select-left  = ["left", "ctrl-b"]    # 左の列へ(選択中のみ)
select-right = ["right", "ctrl-f"]   # 右の列へ(選択中のみ)
confirm      = "enter"               # 確定(挿入のみ)
dismiss      = "ctrl-g"              # 却下(一覧を閉じる)
```

キーバインドに割り当て可能なアクションはこの 6 つ(確定仕様は config-schema.md)。
Tab は `[insert]` の挙動設定に従う(`menu` のときは選択開始キーを兼ねる)ため、独立のアクションにはしない。

## マイルストーン

リスクの大きい順に潰す(非同期収集という最大の技術リスクを最初に潰す)。

### M1: zpty による compsys 候補収集の技術検証(最大リスク)

zpty 内部シェル(現在シェルの fork)で compsys を走らせ、**広げた収集クエリ**(セグメント保持規則を適用したもの)に対する補完候補を吸い出す zsh スクリプトを書く。
参照実装: zsh-autosuggestions の completion strategy(zpty + `vared` + NUL 番兵)、fzf-tab の `-ftb-compadd`(compadd 差し替え)。

検証項目:

- **広げクエリでの候補の正しさ**: ファイル名 / コマンド名 / git サブコマンド / オプションの各補完で候補が取れる。
  あいまい入力の元となるケースを含める:
  コマンド位置の空語で全コマンド名が取れる(`gti` の広げ結果)、
  `docs/inte` の広げ結果(`docs/`)で `docs/` 配下が取れる、
  `--verbso` の広げ結果(`--`)でオプション集合が取れる。
- **compadd フックの網羅性(必須)**:
  `-O`/`-A` 付き呼び出し(マッチテスト用)を候補として数えない、
  接頭辞・接尾辞(`-P`/`-S`/`-p`/`-s`/`-i`/`-I`)込みの挿入文字列の再構成と「置換範囲 = 削った末尾領域」モデルとの整合
  (compsys が語全体の書き換えを前提とする特殊な補完がズレるリスクの検出)、
  表示文字列と挿入文字列の区別。
- **compadd フックの網羅性(あれば良い)**: 説明文(`-d`)とグループ(`-J`/`-V`/`-X`)の取得。
  フェーズ 1 の `zle -M` で表示できるか未定のため、M1 の合否には含めない。
- **pty 出力の清浄化**: `stty -onlcr` 等の設定、
  NUL 番兵による結果のフレーミング、
  `zpty -b` + `zle -F` での部分読みの再組み立て、
  改行を含むファイル名の往復。
- **キャンセルと後始末**: リクエストごとの zpty 作り直し+`zpty -d` によるキャンセル、
  世代番号による stale 結果の破棄、
  数秒かかる補完関数を模擬したキャンセルの実証(非ブロック原則の確認。フォールバック判断の材料にもなる)、
  `zshexit` での掃除、
  再帰防止ガードの動作。
- **計測**: 1 リクエストの端到端レイテンシ(fork〜候補受信完了)、
  大量候補での入力非ブロック(最悪ケース: 数万件ディレクトリ、空語でのコマンド名全収集)、
  連打時の挙動。
  fork のコストは親プロセスのメモリ量に比例する(macOS は特に遅い)ため、`zsh -f` ではなく**実際の .zshrc + 実サイズの履歴を積んだシェルで計測する**。
- `~` を含む入力が展開されずに扱えること。

成立しない場合は「収集のフォールバック」の決定に従い、失敗原因を踏まえてフォールバックを選定してこの plan を更新する。

成果: 検証用スクリプトと、収集方式の結論・計測値を `notes-zpty.md`(このディレクトリ)に記録。

### M2: Rust コア

- `cargo init`。
  `zrush match` / `zrush config` サブコマンドの骨組み。
- `config.toml` パース: 表示(max-lines / delay-ms / min-input)、マッチング(強度: prefix / substring / typo、smart-case)、挿入・確定(Tab 挙動、末尾スペース)、キーバインド。
  不正値は既定値フォールバック+警告。
  config 不在時は全既定値で動作。
- マッチング: `nucleo-matcher` を評価して採用可否を決め、前方一致/部分一致/誤字許容の 3 モード+smart-case とランキングを実装。
- キーバインド記法の正規化(`"ctrl-n"` → `^N`、端末依存キーはシンボリック名のまま出力)。
  デフォルトキーバインド一覧もここで確定する(却下キーの既定は Escape でなく `ctrl-g` を第一候補とする — Escape 単独は矢印キー等の `\e` プレフィックスと曖昧で KEYTIMEOUT 待ちが発生するため。最終決定はここで行う)。
- ここまでを純粋ロジックとして単体テストを整備。
- CI を整備: GitHub Actions で Linux (ubuntu) + macOS の `cargo build` / `cargo test` を回す。
- 成果: `docs/internal/contracts/cli-protocol.md`(zsh↔Rust プロトコル。版不整合検知用のプロトコル版番号を含む)と `docs/internal/contracts/config-schema.md`(config.toml のテーブル・キー・型・既定値の一覧。設定エラーの表示先・タイミングを含む)を作成。
  以後この 2 つを真実とし、コードを追従させる。

### M3: 統合 — リアルタイム候補一覧

- `zle-line-pre-redraw` でのバッファ変化検知 → fd タイマーで遅延(既定 30ms)→ 広げクエリを構築して M1 の方式で候補収集 → `zle -F -w` ハンドラ内で `zrush match`(設定スナップショットを引数で渡す)→ POSTDISPLAY + region_highlight で一覧描画、を通す。
- バッファが空(または空白のみ)のときは収集も表示もしないことを確認。
- min-input・max-lines を config から適用。
  各行は `$COLUMNS` 未満に切り詰め(折り返しによる行数暴れの防止)、行数は max-lines と `$LINES` の小さい方でクリップ。
- `zle-line-finish` で POSTDISPLAY と自前の region_highlight エントリを消去する
  (accept-line 後の残骸防止)。
- 端末リサイズ時の挙動を確認。
- 完了判定: 検証用起動スクリプト上で受け入れ条件 2 相当(一覧の自動表示+大量候補での非ブロック)が確認できる状態。

### M4: 選択・確定・挿入

- 状態依存ディスパッチウィジェットを実装する(キーはすべて config のキーバインド定義から適用):
  ↓ で選択開始(優先順位規則: 途中行→カーソル移動、履歴移動中→履歴戻り、一覧表示中→選択開始、それ以外→既定)、選択中のみ ↑↓=候補移動、Enter/Tab=確定、却下キーで閉じる。
  先頭候補での ↑ は選択解除。
  非選択時は前任者チェーンで元のウィジェットへフォールバックし、↑=履歴・Enter=実行(zsh-abbr の展開込み)を奪わないことを確認する。
  ↑ で履歴を遡った後の ↓ が履歴戻りとして機能することを確認する。
  選択中候補は `selected` の region_highlight で表示する。
- 確定は挿入のみでコマンドを実行しないことを確認する(実行は次の Enter)。
- 確定の置換が「広げ規則で削った末尾領域」のみを書き換え、保持部分とカーソル以降に触らないことを確認する。
- Tab の挙動を config で制御(共通接頭辞のみ挿入 / メニューへ入るだけ / 即挿入)。
  候補未着時の Tab が「収集の前倒し→到着時に適用、0 件なら何もしない」となることを確認する。
- 確定時の末尾スペース付与の有無を config で制御。
- `~/` 配下の候補を確定しても `~` が展開形に置き換わらないことを確認(置換範囲モデルにより保持部分は不可侵)。

### M5: 日常投入と仕上げ

- 設定の mtime 自動反映(プロンプト表示ごとに確認し、bindkey を再適用)。
- 設定エラー時のフォールバック表示(仕様は config-schema.md に従う)。
- zsh-autocomplete を無効化し zrush に切り替えて日常利用開始。
  気になった挙動をこのディレクトリの `notes-dogfooding.md` に記録し、チューニング。
  チェックリストには通常操作に加えて、端末リサイズ・複数行バッファ(継続行)・tmux 内・accept-line 後の残骸・シェル多重起動・zsh-syntax-highlighting / zsh-abbr との共存(Enter での略語展開を含む)・全角文字を含む候補の表示崩れ($COLUMNS 切り詰めが文字数ベースのため)・zsh 5.8 実機での入力圧見送り(`KEYS_QUEUED_COUNT` は 5.9 追加。5.8 では劣化動作)を含める。
  あいまいマッチの順位の体感も確認する(ティア序列は prefix > substring > 誤字許容 > あいまい。
  例: `dcs` では docs(1 文字挿入、未一致接尾辞 0)が
  dash(1 文字置換、未一致接尾辞 1)より上位になる)。
- Linux 実機検証: 実際に使う Linux 環境(SSH 先サーバ / WSL / コンテナ)に導入し、検証用スクリプトで受け入れ条件 2〜7 を確認する。
  zsh 5.8 環境が含まれる場合はそこでの動作確認を最低サポートの根拠とする。
  期間ではなく環境カバレッジの問題のため、main マージ後のフォローアップとして行う(完了判定をブロックしない)。
- 完了判定: 3 日の日常利用(mac)で「使用をためらう問題」が `notes-dogfooding.md` 上でゼロになったら、確定仕様を `docs/internal/specs/`(挙動仕様・config スキーマ)へ昇格し、`docs/user/` に導入・設定ドキュメントを作成して完了。

## 受け入れ条件

1. zsh-autocomplete を無効化し、zrush だけで日常のシェル操作ができる(M5 のドッグフーディングで判定。最低限: cd のパス補完・git サブコマンド補完・コマンドオプション補完・ファイル名補完が各々日常頻度で成功する)。
2. 入力中、候補一覧がプロンプト下に自動表示され、数千件の候補でも入力がブロックされない(取りこぼし・体感遅延なし)。
3. `~` を含む入力が、入力中も候補確定時も勝手に展開されない。
4. あいまいな入力でも目的の候補に到達できる(例: `gti`→`git` のような転置タイプミス、
   `dcs`→`docs` のような 1 文字脱落タイプミスで候補が出る)。
5. 候補一覧から上下キーで候補を選び、確定・却下できる。
   非選択時は一覧が表示されていても ↑=履歴移動・Enter=コマンド実行が通常どおり機能する。
6. フェーズ 1 の全設定項目(max-lines / delay-ms / min-input / マッチ強度 / smart-case / Tab 挙動 / 末尾スペース / 全キーバインド)が `config.toml` で変更でき、次のプロンプトから自動反映される。
7. 不正な設定値でも起動が止まらず、既定値フォールバックが分かるエラー表示になる。
8. Rust 側のマッチング・ランキング・設定パース・キー変換に単体テストが存在し、通っている(CI で Linux + macOS の両方が通る)。
9. 実際に使う Linux 環境(SSH 先サーバ / WSL / コンテナのうち少なくとも 1 つ、可能なら zsh 5.8 環境を含む)で受け入れ条件 2〜7 が成立する。

## 検証方法

- **Rust コア**: `cargo test`(マッチング・ランキング・config パース・キー変換の単体テスト)。
  GitHub Actions で Linux + macOS の両方を回す。
  受け入れ条件 8。
- **zsh 統合**: `zsh -f` から zrush だけを読み込む検証用起動スクリプトを `zsh/` に用意し、受け入れ条件 2〜7 をチェックリストとして確認する。
